open-jev-fast: 5.5× faster Open-Jev-27B inference

open-jev-fast is an inference backend for Open-Jev [1], built by the Open-Jev contributors. It serves the same HTTP API as Open-Jev's jev.server and runs the same model, Open-Jev-27B-v1.1 on Qwen3.8-27B [2],[3], in bf16 with no quantization. The model forward pass is replaced with hand-written fused CUDA kernels, a prefix tree that computes shared prompt text only once, tuned matrix multiplies and CUDA Graphs. All numbers are on one NVIDIA B300.

2. Where the time went

The original takes about 106 ms per request. The moment the CPU finishes issuing all operations is the moment the GPU finishes computing. Each request launches about 5000 GPU kernels, but the GPU is busy for only about 51 ms, so the CPU issuing small operations one by one is the bottleneck. The three main sources:

  • The linear-attention operators (Triton) cost 65–150 µs of CPU time per launch, about 35 ms in total.
  • The LoRA adapter is not merged, so each of the 160 projection layers has an extra fp32 branch. That is 320 extra matrix multiplies, about 20 ms.
  • RMSNorm in Transformers is split into 7 small operations, about 12.5 ms in total.

Also, most of the 7 candidate prompts is repeated text (context and question), and the original recomputes all of it for every candidate.

4. Phase 2: hand-written CUDA kernels and a prefix tree (32.4 → 20.1 ms)

4.1 Hand-written fused kernels (31.0 ms)

All non-matmul operations in each layer are replaced by six CUDA kernels:

  • residual add + RMSNorm
  • SiLU·mul
  • linear-attention prep: causal convolution, SiLU, q/k/v split, head expansion, L2 normalization and the gate parameters
  • gated RMSNorm
  • full-attention prep: QK normalization, partial RoPE and the layout change
  • sigmoid-gate multiply

Matrix multiplies are merged from 9 to 4 per layer. GPU kernels per request drop from about 5000 to 945.

Each kernel reproduces where the Transformers [7] and FLA [4] references round in bf16. On real activations they match bit for bit on 98–100% of elements. The Gated DeltaNet core [5] is still FLA's chunk_gated_delta_rule, and full attention uses PyTorch SDPA.

4.2 Shared prefix computed once (24.4 ms)

The prefix shared by all candidates and each candidate's tail go through one forward pass, so the weights are read once. Computed rows drop from 574 to 364.

  • In the linear-attention layers, each candidate runs its recurrence over its own complete sequence, so the convolution window and recurrent state match the original.
  • The full-attention layers use a tree mask. Related work: shared-prefix attention [12],[13] and tree attention [14],[15].

Long-context tasks benefit most. One task with a 3724-token shared context and 5 options went from 846 ms to 193 ms.

4.3 Matrix multiplies and data movement (22.8 ms)

  • Split-K for down and o_proj, with fp32 partial sums reduced inside the RMSNorm kernel. This is more precise than a single bf16 matmul.
  • Every cuBLASLt heuristic algorithm is timed per exact shape, and the fastest is kept. The full-attention input shape got 23% faster.
  • The gather/cat copies used to replicate the prefix are removed.

4.4 Two-level prefix tree (20.1 ms)

The context is computed once, each question's text once, and each candidate computes only its own tail. For the example request, computed rows drop from 364 to 277. Nodes are not padded to each other and all structure lives in index tensors, so requests of the same size reuse the same CUDA Graph.

5. Why bf16 is hard to push further

Matrix multipliesabout 13 msThe 27B model cannot avoid this compute. This card's measured bf16 peak is 1.76 PFLOPS, and we already reach 70–80% of it.
Linear-attention core (FLA)about 3.7 msFLA's token-by-token version is slower on the GPU (171 vs 77 µs per layer).
Own kernels, attention, gapsabout 3–4 msAnother 1–2 ms could be fused away, but it is a lot of work.
FP8 matrix multiplies (measured, not used)13 → about 7 msThis would bring one inference to an estimated 12–13 ms, but it changes the numerics, so accuracy would have to be re-validated.

6. Correctness

We checked at three levels:

  1. Each kernel is compared element by element with the PyTorch reference on real activations.
  2. Hidden states are compared layer by layer across all 64 layers. The last-token hidden state read by the scoring head differs by 0.19% relative.
  3. All 231 JevBench tasks run end to end with JevBench's TypeSafe adapter and scoring code, and predictions are compared task by task.

The coin-flip task is hard-opus-a-temporal_numeric-09:

  • Original: no/yes = 0.504/0.496.
  • With LoRA merged: 0.503/0.497.
  • Hand-written kernels without the prefix tree: 0.496/0.504.

Any rounding difference under 0.01 flips it, so the flip is unrelated to the prefix tree.

Probability differences grow with input length, because bf16 rounding-order differences accumulate through 64 layers and the recurrent state. They are at most 0.0026 on the example request, and up to 0.035 on the longest request tested (10,722 tokens), where the decision stays the same.

The model card reports 197/231 on public JevBench for this checkpoint. Our run of the original server scored 198/231.

9. Scope, limitations and usage

  • Specialized for one model (Open-Jev-27B-v1.1 / Qwen3.8-27B shapes).
  • Tested only on an NVIDIA B300. The kernels are plain CUDA C++ compiled for sm_103 by default. For another GPU with enough memory, change the -gencode flag in src/ext.py. That path is untested, and the speedups will differ.
  • bf16 only. FP8 matrix multiplies were measured but not used, because they change the numerics.
  • GPU memory: about 96 GiB (98,280 MiB in nvidia-smi after the full JevBench run), so an 80 GB GPU is not enough as is. This covers the weights, the merged and split weight copies, the CUDA Graph pool and activations. The original weights are kept next to the merged copies, so a large part is duplicated; freeing them is not implemented.
  • Requests are processed one at a time.
  • The first request of a new shape captures a CUDA Graph, which adds 1–3 s to that request. Clients should reuse connections (keep-alive).

Setup, correctness tests and benchmark scripts are in the repository README. What is used from each project is listed in THIRD_PARTY_NOTICES.md.
